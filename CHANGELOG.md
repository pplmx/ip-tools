## [Unreleased]

### Added
|- New **`completions`** subcommand generates a shell tab-completion script (`ip-tools completions bash|zsh|fish|elvish|powershell`, written to stdout for your `$fpath`/completions dir) — tab-completes every command, flag and value, driven off the **live** clap argument tree so a future flag appears automatically after a regenerate. A missing/unknown shell is a clean clap error, and an early-closing pipe (`completions zsh | head`, a pager) is tolerated instead of panicking on `BrokenPipe` (Rust ignores SIGPIPE; the old default would print a backtrace for output that is, by definition, disposable). CLI-only (binary-internal), new dependency `clap_complete` (MIT/Apache-2.0, same family as the existing `clap`; MSRV-compatible with the crate's 1.88). Pinned by CLI tests: every supported shell emits a real script naming each subcommand, missing/unknown shells error, and a mid-stream-closed pipe leaves the child exit 0. Resolves the round-17 deferral ISS-122 (DEC-082)
|- The HTTP-family probes (`http`, `http2`, `http3`) now accept an **asserted response shape**: `--expect-status SPEC` (an exact code like `200` or a status class like `2xx`) and `--expect-contains NEEDLE` (a substring of the bounded body snippet). Every per-address observation must satisfy the assertion — a probe that failed to complete carries no response to assert on, so it can never match — and the run exits non-zero with one `expectation violated: <destination>: ...` stderr line per offender when any observation violates, independent of `--strict` (which only gates probes that failed to complete). This turns a single probe into a CI-friendly check for "the endpoint answered the way I asserted" that previously needed a pipe to `grep`; the report on stdout (human/`--json`/`--csv`) is still rendered in full and untouched, and a run without `--expect-*` stays byte-identical. CLI-only (binary-internal `cli` module), no public API change, no new dependency. Pinned by unit tests for the spec parse/matches truth table (`200`/`2xx`, malformed and out-of-range specs rejected) and the violation reason construction (mismatched status, missing needle, failed probe, combination, no-violation), plus fixture-gated CLI tests across HTTP/1.1, HTTP/2 and HTTP/3: a 200 with body `ok` passes exact and class expectations and fails a wrong code/needle with the verdict, a `--sni redirect.invalid` 302 passes `3xx` and fails `2xx` (redirect recorded, never followed), and malformed specs/empty needles error at parse. The repeat form (`probe --protocol http…`) and `diagnose` deliberately stay out of scope (one aggregated `ProbeResult` has no single body to assert on; `diagnose` owns the evidence-rule verdicts) — see DEC-074.
|- Multi-target sweeps (`dns`, `tcp`, `tls`, `http`, `http2`, `http3`, `probe`, `diagnose`) now show a **live per-host progress counter** on stderr (`\r  3/10 hostname`) while a fleet run progresses, instead of a frozen cursor until the whole sweep finishes. It is TTY-gated exactly like the color affordance (a terminal and no `--no-color`/`NO_COLOR`), never shown for a single target, and only ever writes to **stderr** — so `--json`/`--csv`/human data on stdout, and any piped/redirected results, stay byte-clean. CLI-only, no public API change. Pinned by unit tests for the gate truth table (multi-target + terminal + no quiet switches) and the silent no-op, plus a pty smoke check.
|- `diagnose`'s human report now ends with a one-line **verdict trailer** when an anomaly was found — `Anomalies: 2 (HIGH: 1, MEDIUM: 1)` — red when a High-severity verdict is present, yellow otherwise, so a fleet scan's "did anything turn up?" is answered on one colored line without reading every row (a fully healthy run prints no trailer and stays byte-identical). Renderer-only, no public API change. Pinned by report unit tests: the trailer aggregates non-Healthy severities and colors red/yellow for the High/Medium cases, and is absent on a healthy run.
|- Human output is now **colored for a terminal scan**: verdicts carry visual weight — green `PASS` / 2xx / `covers: yes`, red failures / refused/timeout rows / 4xx-5xx / `HIGH` diagnoses / lost route hops / expired certs, yellow warnings (3xx, near-expiry certs, `body: incomplete`, a changed route path), cyan `INFO` severity badges. Color is **strictly gated on stdout being a terminal**, honors the standard `NO_COLOR` environment escape (no-color.org), and can be forced off globally with a new `--no-color` flag; piping, redirecting, pending `--json`/`--csv` and non-TTY output stay byte-identical to the historical monochrome text, so scripts and golden tests are undisturbed. New public API (a tiny `ip_tools::style::Style` type threaded through the `report::render_*` functions; api-baseline regenerated); no new dependency. Pinned by unit tests (plain style is byte-identical; colored style wraps the expected SGR codes; `auto` respects `--no-color`/`NO_COLOR`) and CLI-level checks that `--json`/`--csv`/piped output never carry escapes.
|- `route --count N` now repeats the traceroute N times and aggregates the per-hop observations into a **path-stability view**: how many runs each hop answered in, a min/p50/max latency bound (via the shared `LatencySummary`), the distinct router addresses observed, and a `path_changed` verdict when a hop's router differed between runs — so a flapping next-hop, load-balanced router or BGP/MPLS churn that a single trace cannot show becomes explicit (the repeat view at the route layer, the one probe family that lacked one). `--count 1` (the default) keeps the single-trace behavior, human output and the existing `--csv` format exactly; `--count N>1` adds a `Traceroute (N runs)` human report, `--json` of the repeated `RouteRepeat` (per-hop `RouteHopStats` with distinct addrs + `LatencySummary`), and a repeat `--csv` (`ttl,hostname,addr,rtt_min_ms,rtt_med_ms,rtt_max_ms,answered,runs,path_changed`, addresses `;`-joined when divergent). `--strict` counts a hop as lost when it never answered across any run. Public API change (new `route::traceroute_repeat`, `route::aggregate_runs`, `RouteRepeat`, `RouteHopStats`; api-baseline regenerated); no new dependency. Pinned by lib unit tests (stable path aggregates one router with no change flag; divergent path lists both routers + flags change; lost hops count answered and stay empty; different hop sets union by TTL), a report render unit test, and a `route --csv` repeat render unit test.
|- `diagnose --ipv4` / `--ipv6` now scope the **entire** diagnostic pipeline to one address family (parity with the `tcp`/`tls`/`http`/`http2`/`http3`/`probe` commands): the probed address pool — TCP, TLS (or `--plain`), HTTP, QUIC and the stability repeat — is filtered to the chosen family, so a diagnosis on a dual-stack host whose other family is known-broken (or an operator testing one family in isolation) no longer trips over it. Resolution evidence stays unscoped (both families' DNS answers are still shown), but with only one family's observations the cross-family `AddressFamily` asymmetry verdict is not raised for the family the operator deliberately excluded, and an IP-literal of the wrong family fails cleanly as "did not resolve to any address". No public API change (CLI flags + address-pool routing; the engine's cross-family rules are silenced by the single-family input itself). Pinned by an engine unit test (a single-family TCP input never raises `AddressFamily`, while within-family partial connectivity still fires) and a fixture-gated CLI test: `diagnose <v4-literal> --plain --ipv4` probes the fixture's cleartext 200 with no `AddressFamily` verdict, `--ipv6` exits non-zero with the empty-family error, and `--ipv4 --ipv6` is a clap parse error.
|- The repeated HTTP probes (`probe --protocol http|http2|http3 --count`, and the `diagnose` stability phase) now surface **TTFB** — time-to-first-byte (request sent → response headers arrived) — as its own latency block (`ttfb: min/p50/p95/max` in the human report), `--json` field, and `ttfb_p50_ms,ttfb_p95_ms,ttfb_max_ms` columns in `probe --csv`. Previously the repeats aggregated only total latency, so a stability sweep could not tell a slow-to-respond server (a TTFB tail) from a slow body transfer — the server-response dimension the single-shot `http`/`http2`/`http3` reports already show (`ttfb_ms`). The transport (`tcp`/`tls`) repeats carry no such signal and leave the field empty. Public API change (`ProbeResult` gains a `ttfb: LatencySummary` field; api-baseline regenerated). Pinned by an aggregation unit test (mixed TTFB values summarize into the field, covering failed-but-completed responses), the render/CSV unit tests, and fixture-gated CLI tests: the HTTP repeat surfaces the `ttfb:` block in human output and non-empty `ttfb_*` cells in `--csv`, while the transport repeat row leaves them empty.
|- `diagnose --plain` now runs the full pipeline against a **cleartext HTTP/1.1** endpoint (parity with `http --plain` and `probe --protocol http --plain`): the TLS observation phase is skipped (so a plaintext internal service / captive portal / HTTP-only health check is no longer falsely diagnosed as "TLS handshake fails where TCP connects") and the HTTP phase + stability repeat probe the endpoint over plain HTTP/1.1 via the existing cleartext entry points (`probe_plain_output`, `probe::http_repeat_plain`). `--plain` is mutually exclusive with `--insecure`/`--tls-version`, which only make sense over TLS. No public API change (CLI flag + pipeline routing; http2/http3 are TLS-only protocols and are skipped, cleartext h2c remains out of scope). Pinned by a fixture-gated CLI test: `diagnose <plain-addr> --plain` exits 0 and surfaces the cleartext 200 + `server: ip-tools-plain` response, while the same address without `--plain` is diagnosed TLS-failing.
|- The `http`/`http2`/`http3 --csv` fleet rows now carry **`sans` and `covers` columns**: the served certificate's Subject Alternative Names (`;`-joined) and a `covers=yes` verdict when they cover the presented hostname/SNI — the wrong-host / wildcard-mismatch signal that the human report and `--json` already show but the spreadsheet export dropped, so the cross-host comparison a CSV sweep enables keeps that evidence. The `tls --csv` exporter gains the same two columns for parity. Renderer-only, no public API change (`cert_covers_hostname` visibility widened so the CLI exporter can share the report's matcher). Pinned by unit tests in `src/cli/tls.rs` and `src/cli/http.rs` (a covering cert renders `covers=yes`; a mismatched cert renders the SANs and a blank `covers`; a failed/TLS-less row renders both blank) and the updated `http --csv` fixture header.
|- `diagnose --count N` now sizes the **stability phase** — the number of repeated TCP and HTTP attempts per address that drive the intermittent / HTTP-status-flapping / latency-instability rules (default `3`, matching the sample those rules were validated against; `0` is rejected). Previously the repeat phase hard-coded 3 attempts, so an operator could not trade a longer observation window (for subtler instability) against runtime. CLI-only, no public API change. Pinned by a fixture-gated CLI test: `diagnose <addr> --sni flap.invalid --count 1` suppresses the status-flapping verdict (a single attempt cannot observe 200↔503), while `--count 5` surfaces it — proving the flag is threaded through the repeat phase.
|- The `http`/`http2`/`http3 --csv` fleet rows now carry a **`body_snippet` column** with the bounded response-body text (WAF block page, JS challenge, auth/API error, captive-portal prompt, …) — the content that makes a bare status meaningful, which the human report and `--json` already carry but the spreadsheet export dropped. Quoted via the shared RFC-4180 helper (it may contain commas/quotes). Renderer-only, no public API change. Pinned by an `http --csv` fixture assertion that the row carries the snippet.
|- `dns --csv` single-shot rows now carry a **`records` column** with the actual resolved values (addresses, CNAME, MX, TXT, …) in addition to the latency/TTL — the primary data of a DNS query that the spreadsheet export previously dropped (only human/JSON showed the answers). `--count` repeat rows leave it empty because the aggregation does not retain which records each attempt answered. Renderer-only, no public API change. Pinned by a fixture-gated CLI test: the `dns --doh` single-shot `--csv` rows carry the resolved `192.0.2.77` / `2001:db8::77` records.
|- `diagnose` now **flags cross-address HTTP inconsistency**: when the probed addresses of a hostname return different HTTP response classes (one 2xx, another non-2xx) on the same wire protocol and address family, a Low `Http` diagnosis names the divergent addresses and their statuses — surfacing a partial deployment, a per-node WAF/edge difference, a load-balancer health-check / draining member, or one CDN edge failing. This completes the consistency surface: the engine already compared across protocols and across families, but not across the independently-probed addresses of the same host (the README's CDN/anycast/load-balancing case). No public API change. Pinned by engine unit tests: cross-address divergence fires (200 vs 503 on two addresses); a single address or uniform addresses stay quiet.
|- `dns --count N` repeat rows now carry the **minimum record TTL** across the successful answers (the caching-relevant bound), in the human `ttl: N s` row, `--json`, and the `ttl` CSV column — completing the DNS TTL feature across the repeat surface (previously the `--count` row left the CSV `ttl` empty and omitted it from human/JSON, an inconsistency flagged when single-shot TTL landed). Public API change (`DnsRepeatResult` gains a `ttl: Option<u32>` field; api-baseline regenerated). Pinned by an aggregation unit test (min TTL across a bucket) + the render unit test, and a fixture-gated CLI test: `dns host.example --doh <fixture> --count 3 --csv` carries `ttl=60` on the repeat row.
|- `probe --protocol http --plain` now repeats a **cleartext** HTTP/1.1 request (no TLS handshake) and aggregates the status distribution + latency — the repeat form of `http --plain`, so a plaintext HTTP health/stability sweep works end-to-end against internal services, captive portals or HTTP-only endpoints. New library entry point `probe::http_repeat_plain` (public API change; api-baseline regenerated). `--plain` only applies to `--protocol http` (a non-HTTP protocol is rejected with a clear error). Pinned by a library test (`http_repeat_plain` aggregates 200x3 against the fixture's plain listener) and a fixture-gated CLI test: `probe <addr> --protocol http --count 3 --plain` reports 100% success / 200x3, and `--protocol tls --plain` fails.
|- `ip-tools http ... --plain` now probes **cleartext HTTP/1.1** with no TLS handshake — so internal services, captive portals, HTTP-only health checks and plaintext proxies (where a TLS probe would fail with a handshake error) can be observed truthfully. New library entry points `http::probe_plain` / `http::probe_plain_output` (public API change; api-baseline regenerated); the request path shares the existing request/body/TTFB logic (untouched HTTPS path). `--plain` is mutually exclusive with `--insecure` and `--tls-version`. Pinned by a library test (`probe_plain` gets a 200 from the fixture's plaintext listener) and a fixture-gated CLI test: `http <addr> --plain` renders the `200` / HTTP/1.1 / plaintext server header.
|- `diagnose`'s latency-instability rule (see below) now uses a floored scale base (`max(p50, 1)`), so a **sub-millisecond median on a fast endpoint no longer disqualifies a genuine slow tail** — previously a `p50 == 0` baseline silently skipped a real long-tail flap. No API change; the fixture's slowflap route is now a deterministic fast-fast-slow (mod 3) pattern so any three consecutive repeat attempts expose the tail.
|- `diagnose` now **flags latency instability**: a new engine rule raises an `Intermittent` diagnosis (High confidence) when a repeat probe succeeds at the transport layer with a stable status yet shows a long latency tail (p95 at least 3x the p50) — a degraded backend under load, capacity/rate-limit throttling, or a congested/flapping path that pass/fail counts and status classes both hide. It reads the percentile data the repeat probes already populate (the same HTTP status repeat `diagnose` runs); no public API change. Pinned by engine unit tests (slow tail fires; tight distribution / <3 attempts / transport failures stay silent) and a fixture-gated CLI test: `diagnose <addr> --sni slowflap.invalid` (the fixture alternates fast / ~120 ms responses with a stable 200) surfaces the verdict.
|- `diagnose` now **flags HTTP status flapping**: the repeated-probe phase runs an HTTP/1.1 status repeat alongside the TCP repeat, and a new engine rule raises an `Intermittent` diagnosis (High confidence) when a transport-healthy endpoint observes both 2xx and non-2xx status classes across attempts (e.g. `200` most attempts but `503` on some) — the status distribution the probe path already surfaces (`200x8;503x2`) is now acted on, so a degraded backend, A/B/partial deployment or capacity/rate-limit cycling is visible instead of being hidden by transport pass/fail counts. No public API change (the new rule reads the existing `ProbeResult.status_counts`). Pinned by engine unit tests (flap fires on mixed classes; uniform 2xx / uniform non-2xx / single attempt stay silent) and a fixture-gated CLI test: `diagnose <addr> --sni flap.invalid` (the fixture alternates 200/503) surfaces the flapping verdict.
|- `diagnose --csv` verdict rows now carry the diagnostic **`evidence`** and **`possible_causes`** as semicolon-joined cells (the "why" the human/JSON output already show), so a spreadsheet fleet sweep keeps the reasoning behind each verdict instead of just the category — parity with the TTL/status/header columns. Renderer-only, no public API change. Pinned by the `diagnose --csv` fixture test asserting a row carries its evidence (`TCP path OK; UDP/QUIC path failed`) and possible causes (`QUIC disabled / not offered by server`).

Renderer-only, no public API change. Pinned by the `http --csv` fixture test asserting the fixture's `server: ip-tools-fixture` response header appears in the row.

|- `diagnose` now **flags cross-path HTTP inconsistency**: a host that returns a different response class over one wire protocol than another on the same destination (e.g. HTTP/1.1 -> 200 but HTTP/2 -> 403), or over one address family than the other (IPv4 200 vs IPv6 503), raises a Low `Http` diagnosis — surfacing a CDN edge/WAF treating protocols or families differently, an A/B or partial deployment, or a per-family cloud edge that each path individually "works" through. No public API change. Pinned by unit tests for cross-protocol divergence, cross-family divergence, and the quiet healthy/negotiation-failure/single-protocol cases.

Previously every non-default-port probe advertised the bare host, so an origin server doing host-based virtual hosting on host**+port** routed the request to the wrong vhost or a 404/421 — the probe falsified what is actually served there (RFC 7230 §5.4 / RFC 9113 §8.3.1 / RFC 9114 §4.3.1). Only a non-default port is named, so default-port (443/80) probes are byte-identical; the local fixture's host-keyed routes now strip the port when matching (as `Authority::host` already did for h2/h3). Applied where `@file`/`-` targets are parsed (`tcp`/`tls`/`http`/`http2`/`http3`/`probe`/`dns`/`diagnose`), parallel to the existing `--count 0` and family-scope-empty guards; `route` takes one required target and is unaffected

The h3 row now counts as an HTTP-layer error only for a genuine HTTP/3-protocol failure (`Http`/`Protocol` kind or a non-2xx status); every other h3 failure remains the QUIC path's verdict (`quic_rules`). The reachability rule now stays quiet there and the address-family rule reports the local condition instead, matching how the filtering rule already treats local unreachability (it is not a path/filtering signal). As soon as even one failing address shows a genuine path failure (timeout / refused / reset), partial connectivity still fires with its normal confidence
|- `diagnose` no longer double-counts a QUIC or TLS failure as an HTTP-layer error: `http_layer_rules` used to raise "HTTP-layer errors returned by hostname" for any HTTP-family observation whose transport failed, so a failed HTTP/3 handshake on an otherwise-healthy host produced *both* that HTTP diagnosis *and* the dedicated `Quic` diagnosis for the same cause (and a TLS handshake failure produced HTTP + TLS). The HTTP-layer rule now counts only genuine HTTP-protocol-layer failures (an `Http`-kind error or a non-2xx status) and leaves `Quic` and `TlsHandshake`/`Certificate` failures to their own rules
|- Failed HTTP probes now keep their protocol identity: `HttpObservation::protocol` was only set on success, so a failed HTTP/2 / HTTP/3 probe lost it (rendered as `HTTP/1.1` in the report). Worse, the `QUIC/HTTP3 fails while TCP+HTTPS succeeds` diagnosis and the QUIC-only filtering signal match on `protocol == "HTTP/3"` — with real probes every failed h3 observation had no protocol, so both rules were dead in production. Each probe now tags its base observation with the protocol it is attempting before any step; the human report names the protocol on failure rows too
|- All three HTTP probes now agree on body-read semantics: `body_bytes` is `Some(n)` when the response body completed (end-of-stream or the cap) and `None` when headers were received but the body stalled past the probe timeout. Previously HTTP/2 and HTTP/3 reported a stalled body as a clean partial-body success (a mid-body timeout was indistinguishable from a full reply), and HTTP/1.1 reported a mid-body *transport error* as if the body had simply hit the 1 MiB cap (`Some(MAX_BODY_BYTES)`) instead of a failed observation. Local tests against an in-process `stall.invalid` fixture (headers + one chunk, then the server holds the stream open) verify all three report `status 200`, no failure, `body_bytes: None`

Genuine reset+path-failure combinations still fire (Low confidence)
